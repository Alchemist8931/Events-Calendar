## 2. Секреты Edge Functions

Dashboard → Project Settings → Edge Functions → Secrets. Добавить:

```
YOOKASSA_SHOP_ID      = <shopId из личного кабинета ЮKassa>
YOOKASSA_SECRET_KEY   = <секретный ключ>
PAYMENT_RETURN_URL    = https://<username>.github.io/Events-Calendar/
```

`PAYMENT_RETURN_URL` — куда ЮKassa вернёт пользователя после оплаты.
Должен совпадать с адресом, откуда открывается приложение, иначе после
оплаты человек попадёт «в никуда».

---

## 3. Регистрация вебхука

Личный кабинет ЮKassa → Настройки → **HTTP-уведомления**.

- URL: `https://udhusnopowfnenymsvqg.supabase.co/functions/v1/payment-webhook`
- Событие: **`payment.succeeded`**

Остальные события можно не включать — функция их корректно пропустит.

---

## 4. Почему вебхуку можно доверять

ЮKassa **не подписывает** тело HTTP-уведомления, поэтому доверять ему нельзя:
кто угодно может отправить POST на публичный URL и «начислить» себе денег.

Реализованная защита:

1. Из тела запроса берётся **только `object.id`** — идентификатор платежа.
2. Статус, сумма и `metadata.user_id` запрашиваются **напрямую у API ЮKassa**
   (`GET /v3/payments/{id}`) под нашими ключами.
3. Зачисление идёт только при `status === 'succeeded' && paid === true`.
4. Сумма берётся из ответа API, а не из `metadata` — подменить нельзя.
5. `apply_payment` идемпотентна: повторный вебхук с тем же `payment_id`
   вернёт `duplicate: true` и денег не начислит.

Подделанный запрос не пройдёт шаг 2: у злоумышленника нет валидного id платежа
в нашем магазине.

## 5. Проверка

### Тестовый режим
В ЮKassa включить тестовый магазин, использовать его `shopId` и ключ.
Тестовая карта: `5555 5555 5555 4444`, любой срок в будущем, любой CVC.

### Сценарий
1. Приложение → аватар → «Пополнить» → 500 ₽ → «Оплатить».
2. Редирект на ЮKassa, оплата тестовой картой.
3. Возврат в приложение — появится «Проверяем зачисление…», затем
   «Баланс пополнен: 500 ₽».

### Диагностика
```sql
-- платежи
SELECT provider_payment_id, amount_kopecks, status, applied_at, created_at
FROM payments ORDER BY created_at DESC LIMIT 10;

-- движение по балансу
SELECT amount_kopecks, kind, description, balance_after, created_at
FROM billing_transactions ORDER BY created_at DESC LIMIT 10;
```

Логи функций: Dashboard → Edge Functions → `payment-create` / `payment-webhook` → Logs.

Частые причины сбоя:
- `Приём платежей не настроен` → не заданы `YOOKASSA_SHOP_ID` / `YOOKASSA_SECRET_KEY`.
- Оплата прошла, баланс не изменился → вебхук не зарегистрирован либо указан
  неверный URL; проверить логи `payment-webhook`.
- `no user_id` в логах → платёж создан не через `payment-create` (без metadata).

## 6. Уведомления о биллинге

Ежедневно в 09:41 (`dispatch-billing-notices`):

- **За 3 дня до списания**, если денег не хватает → push владельцу
  «💳 Не хватает средств» с суммой и недостающей разницей.
- **Команда приостановлена** → push «⚠️ Команда приостановлена».

Дедупликация — таблица `billing_notices`, не более одного уведомления
на команду и тип в сутки.

---

## 7. Передача владения

Карточка команды → «Передать владение». Доступно только владельцу,
новый владелец должен быть участником. После передачи списания идут
с баланса нового владельца, прежний остаётся обычным участником.
Действие пишется в журнал как `team.ownership_transferred`.

---

## 8. Юридический минимум перед публичным запуском

Для приёма платежей от физлиц в РФ понадобятся:

- **Публичная оферта** с описанием тарифа (100 ₽ / участник / месяц),
  порядка списаний и условий возврата.
- **Политика обработки персональных данных** — обязательна по 152-ФЗ,
  приложение хранит email и имена.
- **Уведомление в Роскомнадзор** об обработке персональных данных.
- Ссылки на оферту и политику — на экране регистрации и оплаты.

Это не программная задача, но без неё ЮKassa может не подключить боевой магазин.
